## 1. 项目定位

本系统面向**个人内容创作者**（个人博主、技术写作者、学生），解决他们「写作效率低、排版繁琐、存量文章难以检索复用」三大痛点。系统的核心价值在于：**在传统博客的内容管理能力之上，叠加 LLM 的写作辅助与基于私有知识库的智能问答能力**，让"写、管、读"三个环节都更省力。

一句话概括：**一套会帮你写、能替你答的智能个人博客系统**。

---

## 2. 目标用户与典型场景

| 用户类型 | 画像 | 典型场景 |
|---|---|---|
| **个人博主（核心用户）** | 有写作习惯，重视效率，不想在排版和资料整理上花时间 | ① 写技术文章时用 AI 续写/润色卡壳的段落；② 发布前让 AI 自动生成摘要和标题备选 |
| **读者访客** | 浏览文章、想快速找到答案的普通用户 | ① 在站内搜索框提问"如何配置 X"，AI 直接基于博主历史文章回答并给出原文链接 |
| **系统管理员（博主兼任）** | 管理分类标签、审核评论、看站点数据 | ① 定期清理垃圾评论、调整文章分类；② 通过统计面板了解最受欢迎的内容 |

> 说明：个人博客场景下「博主 = 管理员」，通常为同一人，故后台管理功能以轻量、够用为准。

## 4. 优先级分档

### P0（必须做，缺了系统不成立）
- 用户注册 / 登录（JWT 鉴权）
- 文章新建 / 编辑 / 发布 / 草稿 / 删除
- 文章列表 / 详情浏览（Markdown 渲染 + 代码高亮）
- 分类与标签（增删改查 + 归档）
- 评论（发表 / 列表 / 删除）
- **AI 写作辅助（续写 / 润色）**
- **基于私有知识库的 RAG 问答（含流式输出）**
- 后端整体分层架构 + 数据库表结构

### P1（应该做，显著提升可用性）
- AI 标题 / 摘要生成
- 文章搜索（关键词 / 全文）
- 浏览量统计 + 数据面板
- 评论审核流程
- 文章置顶 / 封面图

### P2（可以做，锦上添花）
- AI 自动打标签 / 分类建议
- 评论回复（嵌套）
- 站点基础配置页
- 头像上传、图片上传
- 暗色模式等 UI 打磨

> 原则：**先打通 P0 闭环（写 → AI 辅助 → 发布 → 读 → 问答），再做 P1，P2 视剩余时间取舍。**

## 5. 技术选型建议

### 5.1 前端
| 方案 | 理由 / 说明 |
|---|---|
| **Vue 3 + TypeScript + Vite** | 生态成熟、上手快、社区资料多，适合毕设 |
| UI 库：**Element Plus** | 后台管理界面开发效率高 |
| 编辑器：**md-editor-v3 / ByteMD** | Markdown 编辑与预览一体 |
| 请求：**Axios** | 统一封装 token 与错误处理 |
| 状态：**Pinia** | 轻量，管理用户登录态 |
| Markdown 渲染：**markdown-it + highlight.js** | 代码高亮 |

### 5.2 后端
| 方案 | 理由 / 说明 |
|---|---|
| **Spring Boot 3.x**（Java 17+） | 毕业设计主流、生态完善 |
| 持久层：**jOOQ + PostgreSQL**（沿用现有技术栈） | 类型安全 SQL、已搭建完成，与项目现状一致 |
| 鉴权：**Spring Security + JWT** | 无状态鉴权，前后端分离标配 |
| 文档：**Springdoc (OpenAPI / Swagger)** | 接口自描述，便于联调与答辩演示 |
| 校验：**Jakarta Validation** | 入参校验统一处理 |
| 流式：**Spring WebFlux / SSE** | 承载 LLM 流式输出 |

### 5.3 数据库
- **PostgreSQL**：功能强、支持全文检索（`tsvector`）与 JSON，免费开源，与现有栈一致。
- 备选：MySQL（若导师要求，迁移成本低，但无原生全文检索优势）。

### 5.4 LLM 接入（国内大模型）
| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **DeepSeek（推荐）** | API 兼容 OpenAI 格式、便宜、免翻墙、演示稳定 | 高峰期可能限流 | ✅ 首选 |
| 通义千问 Qwen | 生态好、免费额度多 | 接口格式略有差异 | 备选 |
| 本地部署（Ollama） | 无成本、可离线 | 硬件要求高、质量弱 | 仅演示兜底 |

> 关键设计：**LLM 调用抽象为一个 `LlmClient` 接口**，内部实现用 DeepSeek，未来换模型只改实现类，不改业务代码。

### 5.5 RAG 检索方案
| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **轻量向量检索：PostgreSQL + pgvector** | 无额外中间件、数据同库、运维简单 | 需处理分块与向量化 | ✅ 推荐 |
| Elasticsearch | 检索能力强 | 部署重、毕设过重 | 不推荐 |
| 关键词召回 + LLM 兜底 | 实现最简单 | 召回质量一般 | 兜底方案 |

> 推荐主路径：**文章发布时向量化入库（pgvector）→ 问答时相似度召回 Top-K 段落 → 拼 prompt 交给 DeepSeek 生成回答**。

### 5.6 部署方式
- **Docker Compose**：一套编排 PostgreSQL + 后端 + 前端，本地一键起，答辩演示稳定。
- 前端构建产物托管：Nginx（静态资源 + API 反向代理，解决跨域）。

## 7. 系统架构设计

```
┌─────────────────────────────────────────────────────┐
│                     前端 (Vue3 + Vite)                │
│   前台站点（浏览/搜索/评论/问答）  +  后台管理（写作/管理） │
└──────────────────────┬──────────────────────────────┘
                       │ REST API (JSON) + SSE（AI 流式）
┌──────────────────────▼──────────────────────────────┐
│                  后端 (Spring Boot 3)                 │
│  Controller → Service → Repository (jOOQ)            │
│  ├─ 鉴权：Spring Security + JWT                      │
│  ├─ LLM 模块：LlmClient 接口 + DeepSeek 实现          │
│  ├─ RAG 模块：向量化 + pgvector 检索 + Prompt 拼装    │
│  └─ 全局异常处理 / 参数校验                            │
└───────────────┬──────────────────────┬──────────────┘
                │                      │
        ┌───────▼────────┐      ┌──────▼──────────────┐
        │ PostgreSQL      │      │ DeepSeek API（外部） │
        │ + pgvector      │      │ （写作辅助 + 问答生成）│
        └────────────────┘      └─────────────────────┘
```

**分层职责**：
- `controller`：接收 HTTP 请求、参数校验、返回统一响应结构。
- `service`：业务逻辑，含 LLM/RAG 编排。
- `repository`：基于 jOOQ 的数据访问。
- `common`：全局异常、统一响应、JWT 工具、常量。
- `config`：Security、CORS、jOOQ、OpenAPI 配置。

## 8. 接口设计（REST API）

统一响应结构：

| POST | `/api/auth/login` | 登录，返回 JWT |

| PUT | `/api/posts/{id}` | 更新 |
| DELETE | `/api/posts/{id}` | 删除 |
| PUT | `/api/posts/{id}/status` | 发布/下架/草稿切换 |

### 8.3 分类与标签
| 方法 | 路径 | 说明 |
|---|---|---|
| GET/POST/PUT/DELETE | `/api/categories` | 分类 CRUD |
| GET/POST/DELETE | `/api/tags` | 标签 CRUD |

### 8.4 评论
| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/posts/{id}/comments` | 评论列表 |
| POST | `/api/posts/{id}/comments` | 发表评论 |
| DELETE | `/api/comments/{id}` | 删除评论（博主） |
| PUT | `/api/comments/{id}/status` | 审核（博主） |

### 8.5 LLM 能力
| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ai/assist` | 写作辅助（续写/润色），参数 `type` 区分，支持流式 |
| POST | `/api/ai/title` | 生成标题/摘要建议 |
| POST | `/api/ai/tags` | 打标签/分类建议 |
| POST | `/api/ai/chat` | RAG 问答（SSE 流式，返回引用来源） |

> 设计要点：`/api/ai/*` 全部走 SSE 流式返回，统一由 `AiController` 管理；鉴权上，写作辅助需登录，RAG 问答可匿名（限流保护）。

## 9. 关键业务流程

### 流程一：文章发布 + AI 辅助写作（P0 核心闭环）
1. 博主登录，进入「新建文章」编辑页。
2. 在编辑器写作，卡壳时点击「AI 续写 / 润色」。
3. 前端把选中文本 + 指令 POST 到 `/api/ai/assist`。
4. 后端通过 `LlmClient` 调 DeepSeek，SSE 流式返回结果。
5. 博主采纳/修改，点击「生成摘要/标题」完善元信息。
6. 选择分类、标签，点击「发布」。
7. 后端保存文章，异步触发向量化（写入 `post_embedding`）。
8. 文章对外可见，进入列表与详情页。

### 流程二：读者阅读 + 评论（P0 核心闭环）
1. 访客浏览文章列表，按分类/标签/搜索过滤。
2. 点击文章进入详情页，浏览 Markdown 渲染内容。
3. 访客（登录后）发表评论，进入待审核状态。
4. 博主在后台审核，通过后评论可见。

### 流程三：RAG 智能问答（P0 核心闭环）
1. 访客在搜索/问答框输入问题，如"我之前怎么配置 Redis 的？"。
2. 前端 POST `/api/ai/chat`（SSE）。
3. 后端将问题向量化，在 `post_embedding` 中检索 Top-K 相似段落。
4. 拼装 system prompt（附召回段落 + 原文链接）。
5. 调用 DeepSeek 生成回答，SSE 流式返回正文 + 引用来源。
6. 前端渲染回答，展示可点击的原文链接。

## 10. 难点与风险

| # | 难点 / 风险 | 应对建议 |
|---|---|---|
| 1 | **LLM 接口限流 / 超时 / 返回不稳定** | 抽象 `LlmClient` 接口；设超时与重试；本地存 `ai_assist_log` 兜底缓存；答辩时预备离线演示脚本 |
| 2 | **RAG 召回质量差、回答"幻觉"** | 控制分块大小（500~800 字）；提高 Top-K 相关性阈值；在 prompt 中强制"只依据给定内容回答，无依据则明说" |
| 3 | **向量化耗时影响发布体验** | 发布成功后**异步**生成向量（`@Async` 或消息队列）；问答前检查向量是否就绪 |
| 4 | **SSE 流式输出在前后端分离下的复杂度** | 前端用 `fetch` + `ReadableStream` 解析 SSE；后端用 `SseEmitter`/WebFlux；提前做最小 demo 验证 |
| 5 | **API Key 泄露 / 成本失控** | Key 放环境变量/配置中心，不进代码库；对匿名问答做频控（如每分钟 N 次）；记录 token 消耗 |
| 6 | **安全（XSS / 评论注入 / JWT 过期）** | Markdown 渲染前做 HTML 转义；评论入参校验；JWT 加过期时间与刷新机制 |

## 12. 附录：名词说明

| 名词 | 说明 |
|---|---|
| LLM | 大语言模型（Large Language Model），本系统指 DeepSeek 等 |
| RAG | 检索增强生成（Retrieval-Augmented Generation），先检索再生成，降低幻觉 |
| SSE | 服务器推送事件（Server-Sent Events），用于流式输出 AI 内容 |
| pgvector | PostgreSQL 向量扩展，用于存储和检索文本向量 |
| Embedding | 文本向量化，将文字转为高维向量以支持语义检索 |
| JWT | JSON Web Token，无状态鉴权令牌 |
